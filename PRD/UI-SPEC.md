# Hotel PM Pro · UI-SPEC v1.0

> 版本：2026-09-21  
> 目的：根據 `PRD/SPEC.md` 的民宿 / 包租代管工作流，重設後台第一屏的資訊架構與視覺方向。  
> 本文件只定義原型層級的 UI；不改動 Next.js route、API、資料模型或商業邏輯。

## 1. 設計問題

目前後台以 CRUD 表格為主，`/dashboard`、`/dashboard/properties` 也有部分功能重疊；導覽未完整反映 PRD 的「需求單 / 維修派工」工作流。對每天處理入住、退房、清潔、維修與房東報表的人來說，第一屏應該先回答：

1. 今天有哪些入住 / 退房需要處理？
2. 哪些房間或案件卡住營運？
3. 本月營收與各物業表現如何？
4. 下一個最常用的動作在哪裡？

## 2. 設計原則

- **營運優先**：先呈現今天的房況和待辦，再呈現長期資料管理。
- **一屏可判斷**：KPI、房況、待辦、營收趨勢在桌機第一屏內形成決策閉環。
- **物業脈絡常駐**：全域物業切換器位於 header；所有數字都可讀出目前是單一物業或全部物業。
- **狀態可掃讀**：使用文字 + 色彩 + icon 三種訊號，不只依賴顏色。
- **降低操作成本**：新增訂房、派工、匯出報表、ICS 同步做成四個快速動作。
- **手機可用**：桌機採左側導覽，手機轉為底部 4-tab 導覽與可橫向滾動的內容卡。
- **不偷改產品範圍**：維持 PRD 的繁中、PMS + 物業管理定位；不加入 OTA channel manager、原生 App 或硬體控制。

## 3. 資訊架構

### 3.1 全域導覽

| 群組 | 項目 | 對應 PRD / route |
|---|---|---|
| 營運 | 總覽 | `FR-015`, `/dashboard` |
| 營運 | 房況總覽 | 原型補強；串接 `FR-004` 訂房狀態 |
| 管理 | 訂房管理 | `FR-004`, `/dashboard/bookings` |
| 管理 | 房客 CRM | `FR-003`, `/dashboard/tenants` |
| 管理 | 維修與待辦 | `FR-006`, `FR-007`, `/dashboard/requirements`, `/dashboard/maintenance` |
| 財務 | 月報與分帳 | `FR-008`, `/dashboard/reports` |
| 自動化 | ICS 同步 | `FR-005`, `/dashboard/ics` |
| 系統 | 設定 | 後續 route；原型只展示入口 |

### 3.2 Dashboard 區塊順序

1. Header：問候、日期、物業切換、通知、帳號。
2. Alert strip：需要立即處理的清潔 / 維修 / 待確認訂房。
3. KPI：今日入住、今日退房、本月營收、待處理案件。
4. 房況總覽：物業篩選、房間狀態、入住率摘要。
5. 今日營運：依時間排序的入住 / 退房 / 清潔 / 維修事件。
6. 待辦工作台：案件責任人、物業、狀態、截止時間。
7. 營收趨勢與物業表現：保留月報 / 房東分潤下一步。

## 4. 視覺系統

- **基調**：溫暖的 off-white canvas + 深藍灰文字 + teal 綠作為品牌 / success 主色；橘色只用於需要注意的狀態，紅色只用於阻塞或錯誤。
- **字體**：優先 `Noto Sans TC`，數字使用等寬字體以方便比較。
- **密度**：桌機內容最大寬度 1440px，卡片內距 20–24px，區塊間距 24px。
- **圓角**：卡片 18px、按鈕 10px、狀態 pill 999px；避免所有元素都過度圓角。
- **邊界**：以細邊框和微陰影分層，不使用大面積漸層或強烈玻璃擬態。
- **狀態色**：
  - 已就緒 / 已確認：teal
  - 待處理 / 待清潔：amber
  - 維修 / 阻塞：coral
  - 資訊 / 外部同步：blue
  - 文字灰階：`#18302f` / `#667574` / `#9ba8a6`

## 5. 元件規格

### KPI 卡

- 顯示 label、主數值、與前期比較、狀態 icon。
- 主數值至少 28px；貨幣與百分比用 tabular numbers。
- 點擊後可導向對應列表；原型以 toast 模擬。

### 房況格

- 每個房間顯示房號、房型、狀態；不只用色塊。
- 預設提供全部物業 / 單一物業切換。
- 狀態至少涵蓋：空房、已入住、今日退房、待清潔、維修中。

### 待辦表格

- 欄位：案件、物業 / 房號、優先級、負責人、截止時間、狀態。
- 桌機表格；手機改為堆疊式 row card。
- 只顯示當前最重要的 4–5 筆，附「查看全部」。

### 快速動作

- 新增訂房、建立維修、ICS 同步、匯出月報。
- 所有動作都需有清楚的 verb；避免「新增記錄」這類不具體文案。

## 6. 原型互動

`dashboard.html` 為獨立 static prototype：

- 導覽點擊會切換 active state、更新頁面標題並顯示 toast。
- 物業切換會更新當前 scope 文案與 KPI 的 demo 狀態。
- 通知、快速動作、主 CTA 會開啟簡化 modal / toast，驗證互動層級。
- 不呼叫任何 API、不依賴資料庫、不使用真實個資或 secret。

## 7. Acceptance criteria

- [ ] 開啟單一 HTML 檔即可看到完整 dashboard，不需 build。
- [ ] 桌機具左側導覽、header、KPI、房況、今日營運、待辦與營收區塊。
- [ ] 導覽至少能反映 PRD 的物業、訂房、房客、維修 / 待辦、月報、ICS 六條主工作流。
- [ ] 手機寬度下不出現水平整頁溢出；主要動作仍可操作。
- [ ] 互動有可見回饋，且不假裝已寫入後端。
- [ ] 視覺語言與現有 `dashboard.html` 的 mint 基調相容，但完成資訊架構與營運場景補強。

## 8. 後續正式實作建議

1. 先以本原型與 Sean 確認 dashboard 的資訊架構與視覺方向。
2. 將 `AppNav` 分成「營運 / 管理 / 財務 / 自動化」群組，補上 requirements 與 maintenance 入口。
3. 把 dashboard 的 demo 資料拆成 server-side summary API，避免第一版正式實作直接在 client 端拼裝多個 CRUD response。
4. `房況總覽` 需要補一個以 property / room 為維度的 read model；現有 Prisma schema 只有 Property，不足以表達多房號房況。
5. 月報區塊沿用既有 `/api/reports/monthly`，下載按鈕與實際 PDF response 接線後再做 QA。
